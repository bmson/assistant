# Assistant interaction scenarios — 3 October 2026

This review plays varied owner messages through the actual executor and checks what the assistant delivers and does. It focuses on an assistant that answers the current request, asks for genuinely missing information, keeps its promises tied to completed actions, and recovers without repeating a side effect.

The model is scripted, tool adapters are local frozen results, and each database scenario runs inside a rolled-back transaction on the canonical isolated loopback test database. The real executor, dispatcher, approval resolver, checkpoint recovery, response contract, response-card production, and output-verification funnel remain active. No live model, mail, calendar, reminder, phone, provider account, or production database is contacted. The scenarios measure the machinery around a model; they do not establish the reasoning quality of an actual model.

## Assertions and harness changes

The [replay harness](../../packages/tools/src/question-regression/harness.ts) already runs the real dispatcher and executor in a rollback. It now accepts explicit local evidence outcomes, controlled provider/budget failures, a verifier decision/outage, a rollback-scoped owner timezone, and a prior synthetic task's ledger. An approval continuation uses the actual `resolveApproval` function with queue notification deferred, then executes the same task again. Retryable failure advances the task's eligibility clock locally and resumes the same scripted router. The test never repeats a completed action merely to obtain its evidence.

Rubrics now check exact successful/failed ledger counts, requested argument subsets, local tool-body invocation counts, phase status sequences, owner context reaching the model, typed data-card kinds, and persisted verification flags. Pending or denied ledger rows cannot pass as actual effects. Card-like objects without a `data-card` part cannot pass the new card assertion. The same result retains normal required/prohibited reply assertions. `outputVerificationRevised` records that a revision candidate was returned; it does **not** mean that candidate was published. A rejected review can record attempted/revised/blocked while the original checked reply finishes `done`.

Nine [pure negative grader cases](../../packages/tools/src/question-regression/scenario-grader.test.ts) prove that plausible text does not conceal cancellation no-ops, duplicate writes, sending after denial, duplicate approvals, a wrong timezone window, lost prior context, missing verification evidence, an extra generation beyond the retry bound, or fabricated/mismatched source cards. The latter checks a forbidden weather card, incorrect scoreboard values, and route timestamps that miss the requested meeting. They use no database connection. These checks test the rubric's sensitivity; the integration cases are what exercise runtime behavior.

## Behavior defects and corrections

The actual response contract initially accepted “I cancelled the sunglasses reminder” unchanged when `reminder.cancel` returned `cancelled: false`, including ambiguous matches. It also accepted a creation claim without a reminder identifier. Reminder effects had no dedicated claim/evidence classification. Creation and cancellation now have separate classifications and effect checks, with current-task evidence required and positive receipt cases retained.

The first integration run also exposed an executor enforcement gap: conceptual questions hid tools from the model and requested no tool use, but a model that returned a tool anyway could still dispatch it. The unrelated-calendar scenario keeps an intentionally invalid model proposal so the final tool gate must reject it. “Is my calendar clear tomorrow?” separately failed natural-language read detection; the new availability case requires the actual availability read instead of treating a no-action stop as a valid answer.

Rejecting the conceptual tool revealed a second boundary issue: a tool-only generation then became an empty completion. The runtime now gives that conceptual case one checkpointed tool-free retry, discards any further proposed calls, and leaves another empty completion needing attention. Its dedicated checkpoint flag avoids counting this answer retry as a failed required action in improvement metrics. A separate empty-reply-after-write scenario verifies that this recovery cannot erase or repeat an earlier completed effect.

Final source review found a later recovery path could bypass that tool boundary: an answer that mimics approval prose could trigger a required-tool retry after calls had already been filtered. Two additional adversarial fixtures require one primary generation and no real approval/send for both a conceptual answer and an answer after the forced private read. The final reviewed replay confirms both boundaries: the conceptual failure needs attention; the private read is recovered into a complete ledger-backed answer and finishes `done`. Reading the intermediate accepted capture also exposed an unrequested offer to raise a real approval. The final fallback removes that offer, states that no approval exists, and asks the owner to check Activity before retrying. It does not pretend to have answered the conceptual question.

Finalization also risked marking a task done after it had rewritten an unsupported primary effect claim into a failure explanation. Unsupported requested effects now leave the task needing attention. Golden assertions distinguish a primary missing/failed send (`needs_attention`) from an honest supported send, a clean review, a primary URL-only repair, and a verifier outage (`done`). This distinction avoids turning an answered factual question or an optional reviewer outage into needless owner work.

Reading all 64 retained replies exposed another loss of continuity: an unsupported optional revision could replace an already valid conceptual answer with a generic action-failure notice. The revised flow contract-checks the candidate, then preserves the original checked draft if the candidate is blocked, malformed, falls back to grounding, or requires a deterministic rewrite. Only the delivered draft controls task completion and emotional cues. The rejected candidate's contract/verification telemetry remains available for review. Both a conceptual answer and a completed-reminder receipt now have focused scenarios; separate golden cases cover malformed and invented-link candidates.

Reviewing retained replies exposed two useful recovery details. Ambiguous reminder cancellation now shows a bounded list of validated returned labels, so the owner can choose without guessing. An empty completion after a completed write now retains a current-task verified-effect summary and typed source cards, while keeping `needs_attention` and making no additional model or verifier call. Reminder cards also reject explicit `created: false` or `ok: false` receipts. The final reviewed replay supplies both home/travel choices and the confirmed reminder receipt/card, with one actual creation and no optional review in the interrupted case.

The live-lookup failure path now also retains validated current-task source cards. Mixed calendar/weather failure must show the verified calendar event and no weather card. A rejected numeric score draft must show the actual 5–2 scoreboard beside its verification notice, without asking the owner to repeat an already successful lookup. These remain attention outcomes; their usable evidence is preserved. The historical travel fixture now keeps `arriveBy`, aligns arrival/departure with the returned meeting, and requires a concrete leave time plus buffer. That correction strengthens fixture coherence and acceptance criteria; it does not measure a live model's scheduling judgment.

Complete mail searches now omit their metadata card only when every linked hit was subsequently opened with a successful body-bearing thread read. Empty, incomplete, unread, unlinked, and out-of-order results stay visible. The final reviewed lodging follow-up has its thread card and no redundant search card. Its availability reply leads with the owner's local day and checked calendars; raw UTC boundaries are no longer the headline answer.

## Validation status and limits

The final reviewed scripted all-suite replay passes **67 of 67 cases**, with **zero failed or unrun cases and $0 in model charges**. Every retained case JSON was inspected against its request, including the final fake-approval boundaries and recovery wording, rejected-review preservation, source-card recovery, aligned travel fixture, and tightened assertions. This is serial deterministic executor evidence, not a live-model benchmark or proof that the entire repository suite passes. The latest pure grader run passes all **nine** checks (8.35 seconds); the final focused response-contract run passes all **179** checks (1.77 seconds). The tools TypeScript check, changed-file formatting, document links, and `git diff --check` also pass.

Earlier runs diagnosed behavior: the first passed 315 of 320 checks and found the conceptual-call and availability gaps above, along with a historical status expectation and two fixture issues. The latter were corrected without weakening effect assertions: the mail-provenance scenario avoids the distinct direct-summary tool prohibition, and the recovered-empty-read rubric accepts the truthful phrase “no matching events.” A second batch passed 377 of 378 checks and exposed the empty conceptual completion; the later 381-check batch predates the final refinements. These historical counts are not final coverage. The focused run with the default five-second deadline passed 490 of 493 checks; the three failures were fixture deadlines for the travel case and two 56-entry birthday cases, without assertion failures.

Final canonical full-repository validation completed with exit code 0: **4,600 tests passed across 615 files, with zero skips**, in **1,032.37 seconds**. The command was `FIRESTORE_EMULATOR_HOST=127.0.0.1:8899 GCLOUD_PROJECT=demo-assistant-test pnpm test --testTimeout=30000 --hookTimeout=30000 --reporter=verbose`. The 30-second test and hook deadlines allow the volume fixtures to complete without weakening behavior assertions. All 141 recorded source hashes remained unchanged during the run, binding this result to the frozen local source baseline rather than the base commit alone. The owned Firestore emulator was stopped afterward and port 8899 was closed. This full-suite result complements the final 67-case reviewed replay; it does not establish live-service, live-model, deployment, or physical-device behavior.

There are no repeated same-kind/same-ID cards within any of the 67 final reviewed replies. Only two final reviewed replies have multiple typed cards: score plus route, and calendar plus weather. Both answer distinct requested items; the earlier redundant hotel search card is gone. This is not evidence about duplicate message delivery. Current native response-contract notices display their full replacement text, so their compact transport summaries were not mistaken for hidden user-visible failures. The lodging date mismatch and diagnostic-first lodging prose remain explicit follow-ups; the deliberately adversarial incomplete-answer cases remain attention outcomes. This corpus is not a claim of perfect scenario completion.

Scripted provider/budget outcomes validate executor handling of those outcomes; they do not reproduce a provider's transport, model fallback selection, real prices, or actual reservation cost. Fixed date snapshots validate owner-day interpretation without relying on today's services. The scripted router's `embed` method returns zero-filled 1,536-dimensional vectors. The learned-skill validator rejects these all-zero embeddings, and the executor logs a warning and continues without recalled learned skills. This is an expected harness limitation, not evidence of semantic recall or learned-skill quality. Intercepted saved rows and scripted context prove supplied fact handling but do not establish production graph-memory persistence, embedding quality, retrieval ranking, or contradiction resolution. Structured-card assertions prove server production, while the separate browser and native audits address rendering. Physical voice, push taps, long-session scroll behavior, and real-model conversational judgment remain separate acceptance checks.
