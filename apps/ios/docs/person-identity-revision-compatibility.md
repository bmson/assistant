# Person identity revision compatibility

Identity edits use the revision attached to the person detail shown when the form opened. The read field is `contact.identityRevision`; the update precondition is `expectedContactRevision`. Both carry the same opaque 64-character lowercase hexadecimal native contact revision. The app must keep that value with the draft and must not fetch a newer revision before submitting the old form values.

| Client and server | Behavior |
| --- | --- |
| Older client → revision-aware server | The older client omits `expectedContactRevision`. The server returns HTTP 428 with `error: "review_required"` before changing identity. |
| Revision-aware client ← older server | The person detail has no valid `identityRevision`. Existing-person save stays unavailable and the draft stays visible with a reload message. The client must not invent a revision or send an unguarded update. Creating a person remains available. |
| Revision-aware client → revision-aware server, unchanged contact | The client sends the exact displayed revision in `expectedContactRevision`; the server may update identity if that native revision still matches. |
| Revision-aware client → revision-aware server, stale contact | The server returns HTTP 409 with `error: "conflict"` and performs no write. The form remains open with the draft, disables another save using that old revision, and asks the owner to reopen/review current details. |

The server rendered People editor uses the same rule: its expected revision must match the revision on the dossier displayed to the owner. A separately refreshed snapshot cannot replace the revision attached to displayed values; if they disagree or either is missing, the identity editor remains unavailable until the detail is reviewed again. The legacy web person form passes the revision from its original detail props to the server action. Name, aliases, and relationship are submitted in one revision-guarded command; it does not issue a second relationship write after identity succeeds. Missing revisions show a review-required message and disable the save, while a stale revision leaves the entered values visible and requires reopening the person.

The B2 owner-editor command keeps its existing `expectedContactRevision` field and strict command schema. The legacy mobile PATCH adds the same required precondition and submits its optional relationship in that same guarded command. On a failed or uncertain mobile save, the client preserves the edit and original displayed revision; it does not refresh a new revision behind the draft or retry automatically. For an unresolved web save, “Check result” first reads the same old operation; if that response supplies a reconciliation proof, the next check posts only that proof for the same operation ID. It never resends the private draft or creates another operation. This recovery does not promise indefinite or durable receipt retention. No compatibility fallback sends an update without a revision.
