# Read-only editor release inventory

The dedicated `Observe owner editor release prerequisites` workflow is dispatch-only on trusted main, first attempt only, in the existing protected production environment and `production-deploy` concurrency group. Merging this source does not dispatch it. Dispatch requires a separate reviewed decision. The source is independent of #702/#715; the reviewed #715 manifest is checked out as data only at `04c17b04ab9d76d005b04121927c189baa6edaf9` and must match SHA256 `5baaca10aa089b2eac771de7c9086317206bd937d09a89ea6e937ac945e03cd1`. The identical checked-in fixture is test data, not executable candidate source.

The collector accepts only `--verify-source` or `--collect`, no target or action options. Source mode checks the manifest and fixed workflow/identity configuration before cloud authentication. Collection requires the explicit credential file created by the pinned production WIF action in the workspace: external_account type, exact provider audience, STS token endpoint and configured service account impersonation URL. It does not discover local/default ADC or infer caller provenance from environment variables. No new IAM or credentials are provisioned.

The pinned gcloud 576.0.0 CLI is used for its documented global composite/custom-field lists and explicit WIF access-token acquisition. CLI version is checked before credential/network commands. No `--limit`, collection-group restriction or custom filter is added. The CLI's own fields command filters non-default index configuration (`indexConfig.usesAncestorConfig:false`); the receipt does not claim an inventory of TTL-only inherited fields. The read-only comparison invokes the existing canonical verifier through an in-memory runner, never the mutation-capable preparation path. Missing one approved index is a reviewable classification, not authorization to create it. Unexpected special default configuration remains UNKNOWN because the manifest does not pin its content. A REST-only injected path enumerates manifest groups and deliberately leaves global coverage UNKNOWN; it cannot replace global CLI evidence.

All remaining cloud calls are fixed-target GET requests: database metadata, regional backups only if needed, and agent/web service plus serving-revision descriptions. A private validated URL string is dispatched with redirects rejected. Each read is capped at eight seconds; pagination is eight pages of at most 100 entries and repeated tokens fail. A response is capped at 2 MiB and REST bodies total 8 MiB. CLI commands have the remaining shared 60-second deadline, at most eight seconds each and 2 MiB output per command; retained CLI output totals at most 8 MiB. The same 60-second lifetime includes authentication. Process/API cancellation is best effort, not evidence of remote cancellation. Workflow timeout is five minutes, including dependency setup and authentication, separate from collection bounds. No retries, installs or fallback identities are implemented by the collector.

PITR requires exact database/location/UUID4 identity, valid earliest time and known bounded retention. The original earliestVersionTime wire timestamp is retained exactly; any nonzero sub-millisecond fraction is conservatively rounded UP for comparison, so a preceding whole minute cannot be labeled covered through JavaScript truncation. The separate comparison upper bound is reported explicitly. Observation time is not an operation checkpoint: the receipt leaves operationCheckpoint null and unqualified. It proposes a whole-minute snapshot only when rounding down remains inside observed coverage, separately reports rounding/uncovered milliseconds and projected expiry, and explicitly denies an expiry guarantee. Fresh coverage plus an accepted procedure must qualify any later clone/export timestamp. Backups require exact database name AND UUID4 databaseUid matching the current database incarnation, READY status, valid unexpired snapshot no older than 26 hours; a recreated same-name database cannot borrow its predecessor’s backup. Backup receipts preserve the exact snapshot and expiry wire timestamps. Snapshot age uses a conservative floor, future-snapshot rejection uses a ceiling, and expiry uses a conservative floor; separately labeled comparison bounds cannot be mistaken for the actual snapshot. Backup receipts explicitly report the uncovered interval. Neither proves restore success. Service observations retain only allowlisted release fields, account, immutable image, serving revision and hashes of configuration; raw API bodies, private environment values and tokens never enter the artifact. Serving revision image, account and release fields must match the service template. Signed-image provenance, retained recovery pair, worker configuration and approved recovery procedure are not established by this collector. The 64 KiB receipt always denies traffic, maintenance and mutation authority.

Actual compatible retained guarded recovery pair/configuration and an accepted recovery procedure are required **before the first candidate traffic or ordinary contact writes**, even with editing disabled. A newly built same-source pair is only a candidate, not demonstrated known-good recovery. A safe qualification proposal must keep traffic and ordinary writes closed while checking immutable source/build provenance, disabled service readiness and recovery configuration; no such staging action is performed or authorized by this source. Older acbd source is not presumed compatible with #702 authority or #715 binder data. All binder-writing maintenance, including provision-disabled and disable, remains forbidden until old serving, inflight and recovery parsers are retired.

Exact retention protection is a separate source change documented in `recovery-retention.md`; no active allowlist is supplied. The collector does not change cleanup, pause ingress, drain workers, create indexes, rotate epochs, migrate databases, deploy code or enable editing. Its artifact cannot authorize any of those actions.
