# MCP OAuth release compatibility

MCP OAuth is optional and defaults to off. API contract 3 marks the web and agent pair that enforces OAuth grant generations at dispatch. It is independent of the Calendar write contract. Both sides declare peer range 3–3. Firestore stays at storage schema 1 because its OAuth record field is additive. A pre-OAuth worker can still read these documents, so matching Firestore schema versions alone cannot qualify a mixed pair.

PostgreSQL migration `0138_mcp_oauth_state` adds nullable OAuth state to existing MCP connection rows and installs a trigger to fence stale grants after a connection change. Existing records start with SQL NULL state, so the migration needs no credential backfill. The current release declares PostgreSQL schema 138 for every packaged role. The image qualification job applies the exact forward migration tail to populated schema 134, checks the ledger after a second migration run, and reads back an existing manual MCP connection along with the existing memory, Calendar, and budget fixtures.

Use a separately reviewed drained full-pair transition from a pre-OAuth deployment. The ordinary release preflight rejects both mixed API combinations. Legacy Firestore bootstrap remains restricted to its pinned historical release. Keep OAuth off while establishing the new pair. Before enabling the flag, verify the exact serving revisions and manifest, matching owner and storage, and matching registration and encryption configuration across web and agent. The runtime predicate checks local declarations and maintenance fences. Release admission must establish what is actually serving.

## First protected Firestore API 1-to-3 release

The production workflow holds this transition until a source-bound forward recovery from a mixed parked pair is independently verified. The intended entry point is a new first-attempt manual dispatch for the exact current main source and the full Firestore pair. Start with a reviewed compatible-OFF spending profile, no activation drain packet, and optional MCP sign-in off. Before maintenance, qualify exact source CI, all five signed images, the current owner/privacy-bound READY epoch through the actual deployment identity, index parity, and recovery. Temporary read access and any deployment authorization are separate.

Independently hold delivery and settle the original processes. Capture both original API 1 revisions and their prior automatic scaling. Close both services at explicit Manual0, with each original revision the sole untagged route. Bind these observations, closure, drain, and recovery in a fresh disabled bootstrap for the new source. Use the existing operator-owned workflow holds and competing-run census. The transition refuses open or mixed old revisions, changed native bindings, a foreign peer URL, or an inherited enabled MCP OAuth setting. A same-version ordinary release still runs the ordinary peer compatibility check. PostgreSQL uses its existing separate upgrade constraints.

The release creates a named, paused agent revision with zero canonical traffic. It adds the candidate tag by exact revision name after reading back the revision and verifying its source, run, manifest and pause setting. Creation uncertainty stops before tag attachment. The paused web canary checks that the exact paused agent revision answers through its tag. The ID token audience stays the canonical agent service URL. After the exact successor is canonical and its automatic scaling is verified, the paused web canary requires that successor's matching source, manifest, revision and write state. Both web and agent explicitly set MCP OAuth off in a disabled API 3 bootstrap, including an API 3 forward rebuild. API 1 keeps its existing probe order.

### Recovery states during the hold

Keep the original and candidate evidence before a service write. Read both native services and all revisions in desired or observed traffic, including zero-percent aliases. Preserve each attempt, unknown result, completed operation, and fresh readback. Resolve uncertain operation outcomes using GET only. Keep delivery held while reconciling.

| Observed state | Required evidence before a recovery action |
| --- | --- |
| Original closed pair, with no new revisions or tags | Revalidate both exact original service and revision bindings, including the latest template, Manual0 and the sole untagged canonical routes. Reopening either original requires its own settled admission and drain review. |
| Candidate alias points to the original agent | Treat the alias as a potentially reachable route. Bind its exact name, target, current etag, and the captured original and unrelated routes before reviewing a traffic-only closure. Verify desired and observed closure and settle requests and processes exposed by that alias. If either template or its latest revision changed, the original bootstrap receipt cannot be reused. |
| Only paused candidates created or tagged | Confirm the exact candidate source, manifest, signed role images, pause flag, and absence of any unpaused intent. Acknowledge that candidate creation may have changed the latest template even when canonical traffic still points to the original. Close the exact attempt-owned aliases, verify canonical closure and settle exposed processes before a new operation. |
| Paused API 3 web with old agent still canonical, including uncertain agent successor creation or promotion | Preserve the candidate and successor artifacts and delivery holds. Independently close and settle every route that may have admitted work. A forward recovery must establish a coherent, closed API 3 web and agent pair with proven source, manifest, actual role images, and matching latest templates. Closure of the old agent tag or repointing one traffic row does not by itself establish this pair. |
| API 3 agent promoted or web resume may have been created | Keep marker-aware images and jobs. Use exact observed revision identities to close and drain API 3 admissions under a separately reviewed recovery. The release never reopens the API 1 pair after the agent successor may exist. |

The protected run archives bounded successor intent and outcome files along with the existing manifest, creation and barrier artifacts. An existing disabled API 3 bootstrap starts from an already coherent pair. It cannot repair the mixed-parked state in the table. This source requires verification of that missing recovery step before the production compatibility exception can succeed.

After successful promotion, verify both API 3 revisions, their common source and manifest, owner/storage and MCP OAuth OFF. The protected inventory now recognizes coherent API 3 Firestore pairs. Subsequent budget baseline and spending activation still require their own existing evidence and approval. Leave optional MCP sign-in off unless separately authorized.

During rollback, keep dispatch and account writes paused until the target pair is checked. An OAuth-capable pair with the flag off must still recognize stored OAuth grants and refuse fallback to the manual credential on those connections. Returning to a pre-OAuth pair requires disconnecting or removing OAuth-enabled connections under the current implementation, verifying the persisted readback, and draining queued and in-flight activity before starting the older binaries. PostgreSQL rollback requires a previously qualified schema-compatible target or a separately reviewed database recovery. Keep the migration forward-only in normal releases.
