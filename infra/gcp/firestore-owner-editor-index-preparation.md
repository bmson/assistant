# Owner editor index preparation

This manually dispatched production workflow prepares one Firestore composite index using trusted `main` workflow and script code. It checks out the approved source commit `61c74edd9c67a77814d148565fb82651c0e2091e` into a separate sparse data-only directory, then reads its manifest with `git show`; it never executes that commit's code. It does not deploy application code or change single-field exemptions. The approved manifest is pinned to SHA-256 `5baaca10aa089b2eac771de7c9086317206bd937d09a89ea6e937ac945e03cd1`; its only delta from baseline commit `236a35a5e05163855c9b708414bf389d90cd15c2` (manifest SHA-256 `f76e7670a29973fe21394b3a96220846b006ca7783efa412235a8550d8163be6`) is the `ownerEditorOperations` index on `ownerId ASCENDING`, `formIssuedAt ASCENDING`, `id ASCENDING`.

The workflow reuses the existing production `GCP_PROJECT`, `GCP_WORKLOAD_IDENTITY_PROVIDER`, and `GCP_DEPLOY_SERVICE_ACCOUNT` variables. Its GCP calls are limited to index list/get and one composite-index create; it issues no IAM changes, field updates, or index deletes. Missing identity configuration fails source preflight before cloud authentication.

Dispatch **Prepare owner editor Firestore index** from `main`. The target is fixed to project `bmson-assistant`, database `assistant-production`, region `us-west1`; the source preflight rejects any other project or database before cloud authentication, and unknown command-line arguments fail before source or cloud work. The workflow runs only on its first attempt and has a 45-minute ceiling. It verifies source hashes and delta, then confirms the active gcloud principal is exactly `GCP_DEPLOY_SERVICE_ACCOUNT`. It calls Policy Troubleshooter v3 once per required permission at the exact Firestore database resource, requiring a `CAN_ACCESS` result and a visible direct, unconditional grant to that service account. The guard checks `datastore.indexes.create`, `datastore.indexes.get`, and `datastore.indexes.list`; Firestore documents map field `get` to `datastore.indexes.get` and field `list` to `datastore.indexes.list`, so no `datastore.fields.*` permissions exist. Missing, conditional, denied, malformed, unknown, or incomplete explanations stop the run before Firestore inventory reads. No IAM grants are added. If the existing production identity cannot inspect all applicable policies with Policy Troubleshooter, the workflow stops.

The Policy Troubleshooter request is `POST https://policytroubleshooter.googleapis.com/v3/iam:troubleshoot` with `{"accessTuple":{"principal":"<GCP_DEPLOY_SERVICE_ACCOUNT>","fullResourceName":"//firestore.googleapis.com/projects/bmson-assistant/databases/assistant-production","permission":"<one required permission>"}}`. This uses the active production identity's access token. The response must match the requested tuple, report `overallAccessState=CAN_ACCESS`, `allowAccessState=ALLOW_ACCESS_STATE_GRANTED`, and `denyAccessState=DENY_ACCESS_STATE_NOT_DENIED`, contain no unknown/unspecified enum state, include corresponding policy/binding explanations, and show at least one direct `serviceAccount:<email>` binding whose role contains that permission and whose binding and explanation have no condition fields. Indirect membership alone is insufficient.

The API schema and required permission mapping are based on Google's [Policy Troubleshooter v3 method](https://docs.cloud.google.com/policy-intelligence/docs/reference/policytroubleshooter/rest/v3/iam/troubleshoot), [Firestore IAM permission mapping](https://docs.cloud.google.com/firestore/docs/security/iam), and [Firestore Admin audit permission mapping for GetField/ListFields](https://docs.cloud.google.com/firestore/native/docs/audit-logging). The database full resource name follows Google's [Cloud Firestore resource-name example](https://docs.cloud.google.com/eventarc/docs/path-patterns). These are source-level references only; no production permission request was made.

Before creation and again after READY, the script paginates the deploy workflow's complete run history (up to 5,000 records and 30 seconds). It recognizes queued, in-progress, waiting, requested, and pending as nonterminal. Each page is limited to 100 rows; every row needs a unique positive run ID across the full listing, and observed rows must agree with the stable API total count. Pagination links must remain on the exact repository's `deploy.yml` run endpoint, use the expected page size, and advance one page at a time. API errors, repeated or malformed IDs, wrong pagination paths, incomplete/changing pagination, unknown statuses, and exceeding any bound fail closed. It refuses inventory drift, creates at most the single approved composite index through the canonical provision helper, applies zero field overrides, waits through the canonical readiness verifier, and checks the full approved manifest. An active older `main` deploy blocks the workflow; review the deploy result and dispatch a new run after it finishes. Workflow concurrency shares `production-deploy` and does not cancel a deployment.

This procedure does not make index preparation atomic with a concurrently dispatched workflow or merge. Serialize main merges and production dispatches around the run. The checks fail closed on visible queued/running deploy runs, but a new deployment dispatched after the final check remains a serialization limitation.
