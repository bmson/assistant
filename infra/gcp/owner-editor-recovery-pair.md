# Bounded recovery proof collection

This is a separate, default-off read mode of the existing protected inventory workflow. Source publication, a final owner approval, a workflow dispatch, actual collection, offline verification, recovery compatibility and deployment are separate gates. Adding this source grants no operational approval. Do not enable held deployment/cleanup/import workflows or change IAM to make collection pass.

Select `recovery-pair` only after independent source review and tests. Supply the exact approved current main SHA, an absolute UTC start deadline no more than 30 minutes ahead, and an existing operator-controlled RSA public recipient key (3072–8192 bits). The private key stays with the operator. The production environment and `production-deploy` concurrency remain in force; only trusted main and first attempts run. `prerequisites` is still the default and retains its existing observer and pinned authentication action. Recovery mode does not run the prerequisites collector, gcloud, Docker or the pinned auth action.

Recovery source preflight checks project, deployment service account, repository, ref, workflow identity, first attempt, checkout/workflow/source SHA equality and approval window before authentication. Recipient validation also precedes authentication. Current effective WIF/registry access is unknown. Permission denial stops; no role grant, user credential, local/default ADC, fallback identity, login, OAuth refresh, impersonation setup or permission repair is supported.

## Explicit authentication contract

The pinned `google-github-actions/auth` action cannot implement this mode's three-request budget unchanged: its outer OIDC retry wrapper permits four calls, and the bundled OIDC client permits eleven primary GET attempts per call, plus redirect hops. Its Google HTTP client permits redirects; its configured retries do not make POST retries (the bundled retry verb allowlist excludes POST). The action has no exposed zero-retry/no-redirect input. Reusing it would require a separately approved larger contract, not a false zero-retry assertion. The existing prerequisites mode is unchanged.

The recovery-only Python adapter performs exactly one GitHub OIDC GET, one STS token-exchange POST and one IAM access-token mint POST, with no redirects, proxies or retries. It uses the same configured WIF provider and fixed `assistant-github-deploy@bmson-assistant.iam.gserviceaccount.com`, requesting the same cloud-platform scope as the existing WIF client and a 600-second impersonated token. STS performs signature/identity validation; local claim checks additionally bind audience, repository/ref/source/workflow and run/attempt. A failed exchange does not authorize additional permissions. Each response is at most64KiB, each socket timeout at most8s, and the parent kills the auth worker at30s. Auth is distinct from the registry budget. No token, request header or credential file is written, printed, output to Actions or included in artifacts; the private process pipe is closed and the worker reaped on success/failure/deadline. Python memory clearance is not claimed as cryptographic zeroization.

The supported closed OIDC runner profile is exactly `https://pipelines.actions.githubusercontent.com` with no explicit port, credentials or fragment. Arbitrary GitHub subdomains are not aliases. An unsupported legitimate runner profile stops before the request token is read or forwarded; no suffix match or endpoint fallback is allowed. The pinned action gets its endpoint dynamically and does not prove this particular hosted run uses the supported profile. That compatibility remains unobserved in this source-only preparation. This restriction closes an allowlist gap; it is not evidence that an attacker controls GitHub subdomains.

## Collection and evidence

The collector is pinned to the retained 9df source pair:

- `us-west1-docker.pkg.dev/bmson-assistant/assistant/agent@sha256:1e87cc4b87922f6f9b59216afff045af49be8aac40601cb2d07a1723d7fc7c87`
- `us-west1-docker.pkg.dev/bmson-assistant/assistant/web@sha256:9e51884069d0c1a2c74115b98a0b9818a8b8d6d4cc726b444a86439b6b3ebac7`

It permits at most24GETs,16MiB combined response bodies and120s under a parent-process deadline; socket timeout is at most10s. Failed GETs consume budget. Only those subject manifests, their digest-derived `.sig`/`.att` manifests, and bounded proof blobs explicitly described by those observed manifests are allowed. These proof blobs are signature/attestation objects, not runnable image layers. Tag enumeration, image config/layers, other repositories, redirects, retries, external trust endpoints, Cloud Run, Firestore and provider calls are excluded. Digest, descriptor length, media type and per-manifest layer caps fail closed. Unsupported layouts stop without an OCI-referrer fallback or new allocation.

Raw objects live in one exclusive0700 runner-temporary directory. A fresh private ownership nonce binds cleanup; existing paths are never reused or treated as owned merely by name. The plaintext objects and ownership state are not artifacts. The envelope uses AES-256-GCM with purpose-bound AAD and RSA-OAEP-SHA256 wrapping to the existing recipient; only that encrypted file is retained for one day. A closed sanitized outcome is retained14days, with unknown counters left null. The `always()` cleanup step removes only nonce-proven raw objects/state on ordinary success/failure/cancellation. Runner loss, hard termination or cleanup failure cannot prove deletion; report that state separately. Tokens have no disk path to clean.

Cleanup runs before outcome publication. A cleanup exception retains `cleanup: failed_unknown` and `status: cleanup_failed_unknown` before failing closed, suppressing raw exception/path/token text and any success disposition. The unknown cleanup is not blindly repeated by the later cleanup step. A receipt-write/storage failure still cannot establish a retained outcome or deletion; it remains a failed job.

If cancellation occurs after nonce-proven ownership/raw-directory creation but before a collection receipt exists, cleanup first snapshots that source/run proof and creates an `interrupted_unknown` receipt with null auth/registry counters and the actual cleanup disposition (`completed` or `failed_unknown`). A failed cleanup is not retried. No proven owned state produces a distinct `no_owned_attempt` outcome with cleanup `not_attempted`; it does not prove zero remote work. Unverifiable ownership produces `ownership_unknown`/`failed_unknown` without deletion. No exception, private path or nonce is included. Failure before checkout/helper availability, runner loss or inability to retain the receipt remains unknown.

Collection reports `cryptographicVerification: not_performed`. The pinned Darwin-arm64 Cosign and authenticated trust root remain local, offline and network-denied. This Linux job does not run that binary, download another verifier or claim signature success. Separately approved retrieval/decryption and offline verification must check exact signed subjects, expected GitHub signing identity/source, certificate/SCT/transparency proofs and SBOM correspondence. Current recovery config/API/schema compatibility, writer drain, epoch readiness, live deployment/serving and installed/native acceptance remain separate.
