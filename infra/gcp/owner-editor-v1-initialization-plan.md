## Required initializer behavior

Use the existing `packages/firestore/src/owner-editor-repository.ts` V1 helpers from the exact candidate. The current rotation helper is maintenance-only and always chooses a fresh UUID; invoking it on every retry is **not idempotent**. Ordinary editor GETs correctly return unavailable for missing or disabled metadata and must stay read-only.

The initializer must offer a dry-run that performs no writes, accepts only the reviewed fixed project/database/installation/owner context, and checks the singleton owner, current privacy state, expected epoch absence or exact existing disabled state, and proposed result. Keep owner/privacy/epoch details in the bounded private approval material, not CI logs or public receipts. Stop for active privacy erasure, malformed metadata, unexpected existing READY authority, target mismatch, or changed preconditions. Missing and completed privacy generations use the production helper's exact native timestamp token/digest.

Production application must be one Firestore transaction. Read owner, privacy job, current epoch and all comparison inputs before writing. Compare against the approved absence or exact prior document/version and privacy state; a concurrent change must abort rather than silently rotate/rebind. Write only the single existing-format maintenance cursor (name, updatedAt, and JSON cursor with exactly ownerId/epoch/ready/privacyGenerationDigest). No agent, contact, family, memory, operation, schema, or V2 document may be written. Factor the existing helper's record construction/privacy binding into one shared internal maintenance helper accepting a validated proposed epoch UUID; keep ordinary rotation calling it with randomUUID(). The initializer calls it with the preapproved UUID after the extra compare-and-set reads. This small source change requires its own review and tests. No browser/API input may select an epoch.

Before approval/application, generate one proposed UUID and persist it in the private review packet with the operation identity, exact before-state/version, target owner/workspace, privacy digest, candidate SHA and expiry. The packet survives runner loss; it is not printed in ordinary receipts. Every transaction attempt uses that same UUID, so a crash after commit has a recognizable result without a new document or schema. First verify the current singleton owner and privacy token. If the epoch equals the exact proposed four-key result and remains privacy-bound, return already_applied without a write. Otherwise require the exact approved absence or disabled before-state/version; any distinct state aborts. A reviewed disabled epoch may be enabled only by that explicit transition. The original random-UUID helper alone cannot implement this replay contract. If provision-disabled then enable is chosen, use two separately approved packets with distinct proposed UUIDs and exact predecessor states; never restore or reuse an old ready epoch.

A dry-run receipt cannot authorize later writes indefinitely. Bind application to the reviewed identities, exact candidate SHA, before-state, privacy generation, expiry, and operation identity. Record only sanitized outcome and evidence references. Required tests include: missing create, already-applied replay without rotation, disabled approved transition, unexpected READY rejection, concurrent epoch/privacy/owner change, active erasure, crash-after-commit replay, and failure leaving all other collections untouched. No executable in this patch implements or qualifies that behavior.

If a release fails before guard execution, there are no guard mutations to roll back. If initialization succeeded but candidate rollout then fails, do not restore an old epoch or invent a ready flag: follow the separately reviewed disable/recovery transition and retained marker-aware pair. Disabling must invalidate admission safely and have the same privacy/concurrency/replay safeguards. User data rollback and metadata disable are separate decisions.
